# 校园网防共享项目调研与验证清单

本文记录对已调研项目的实现原理、可借鉴部分、风险边界，以及 OneNetShare 第一批改造的验收方法。结论是：只借鉴机制与验证方法，不复制配置、阈值、DPI 特征或他人的认证参数。

## 一句话结论

- 最值得借鉴：门户自报探测、本机 `OUTPUT` 与 LAN 转发画像不一致、出站封堵顺序、画像一致性自检、看门狗/计数器验证。
- 最不该照抄：各学校的 `jsVersion`/AC IP/错误码语义、DPI 特征、ShellClash YAML、固定阈值、GPL/未授权代码资产。
- OneNetShare 的定位仍是“单一画像出口 + 只读诊断证据”，不做自动校园认证，不做 HTTPS MITM。

## 项目实现原理与可借鉴点

### nicker3915/tianyixiaoyuangongxiang

- 原理：PowerShell 包装本地 ESurfing 客户端，通过 localhost API 轮询认证/在线/热点状态；用具名 Mutex、进程三要素归属校验、原子文件替换、watchdog 与冷却/限速实现恢复。热点由 WinRT `CreateFromConnectionProfile` 创建，按 GUID 记录归属；`managed-routes.json` 只添加/删除精确路由，发现他人路由冲突即拒绝启动。
- 可借鉴：状态机边界、进程归属校验、冲突即停、精确 tuple 清理、日志脱敏、pause flag、恢复冷却。
- 风险/不借鉴：仓库为归档，无 LICENSE，认证组件许可证不在归档内；硬编码 IP/任务名/AppId、明文凭据、环境耦合参数不能复制。该项目未实现 TTL/MAC 伪装或多设备检测绕过。

### moonkagariqaq/CampusLink

- 原理：EsurfingGo 二次开发的 Windows 认证客户端；captive 探测→解析 `config.campus.js`→ZSM 协商→ticket/login→心跳/下线。新增 C# 层提供服务化保活、命名管道控制面、DPAPI 凭据保护、ACL、物理网卡绑定，以及“认证在线后再启动热点”的 extras 工具。
- 可借鉴：认证 socket 绑定物理网卡、凭据不进命令行、UI/服务/认证子进程分离、只读状态管道、热点后置动作“限时等待状态→执行→退出”、敏感日志早脱敏。
- 风险/不借鉴：新增 C# 代码未声明许可证；下载模块/凭据/订阅不可复制；停止官方客户端服务必须显式授权并支持回滚。国内 IP 绕过 TUN只是本机 Clash 经验，不是仓库实现。

### EOYOHOO/Campus-network

- 原理：OpenWrt 路由层多设备检测绕过，重点是把终端指纹收敛到路由器一层，结合 NAT/防火墙规则控制出站行为。
- 可借鉴：路由器作为单一身份出口；转发面与本机面分开验证；组播/广播/QUIC/DoT 等旁路协议需要显式处置。
- 风险/不借鉴：具体规则、阈值、上游地址属于环境经验；OpenWrt iptables/nft 细节不能直接用于 Windows，但诊断方法可参考。

### fuhuafash/campus-network-guide

- 原理：把多设备检测拆成 DHCP 指纹、MAC/OUI、TTL、HTTP UA、域名特征、NTP、TCP 连接数、TCP SYN、DPI；文档建议用逐级实验定位触发维度，并给出 OpenWrt TPROXY/UA3F/NTP redirect 方案。
- 可借鉴：检测维度清单、逐级验证法、硬件性能警告、按账号/公网 IP 连接数与 CPS 观测、规则分类（域名/CIDR/端口/网络）。
- 风险/不借鉴：仓库 GPL-3.0，配置/文档整体复制会产生派生风险；桌宠素材另有 CC-BY-NC-SA；DPI 特征、固定阈值、OUI/UA 表不要内置。HTTPS UA 不应靠 MITM 强行改写。

### YifanHere/campus-net-nat-bypass

- 原理：以福建农林大学为例，门户页面通过 JS 私网图片探测、WebRTC、Windows ActiveX 自报 NAT 信息，Referer 泄漏 OS 探测域名；路由器本机 `OUTPUT` 探活与转发面 UA 不一致；解决方向是统一 UA、L3 重建 TCP、封堵 portal 直连、DROP QUIC/组播/DoT、限制并发与新建连接速率，并区分 IPv6/MAC 画像。
- 可借鉴：门户自报探测清单；`RETURN` 早于 `DROP` 的链顺序；看门狗与幂等规则；计数器/conntrack 验证；错误码分流（已在线成功、封停静默、凭据错停手）；全链路验证清单。
- 风险/不借鉴：`jsVersion`、AC IP、`,1,` 前缀、阈值、LAN 段、HAR 参数只适合作者环境；MTK HNAT 是 OpenWrt 平台问题，不是 Windows 机制。

### qinjackson.github.io/posts/campus-network-openwrt

- 原理：作者环境只有 UA 检测，因此以 UAmask 统一 HTTP UA 为核心，辅以 TTL/IPID/NTP、自动登录、设备管控；强调路由器自身流量也必须统一画像，并指出 MTK HNAT 会让逐包规则被卸载流绕过。
- 可借鉴：UA 是最基础画像；本机面与转发面同时验证；身份确定后运行中不要改 MAC；错误码退避（A 型 600/900 秒、B 型夜间静默）可作为未来自动登录规格。
- 风险/不借鉴：其环境结论“443 天然绕过”“只改 UA”不是普适结论；脚本中 IPID 实际只打 mark，并未改写 IP ID；固定 UA、设备管控、每日重拨不适合照搬。

### aky.moe/阻止多设备检测

- 原理：文章页面抓取不完整，已确认主题是阻止多设备检测，细节不足以形成可执行规则。
- 可借鉴：仅作为“还有浏览器侧画像维度”的提醒；不据此实现具体规则。

### Misyra/campus-auth-tasks

- 原理：任务 JSON 描述校园网登录步骤，执行器 Campus-Auth-rs 支持 http/playwright/script 等任务。
- 可借鉴：若未来做自动登录，只考虑 `http` + `schema_version: 2`，并严格隔离凭据、错误码、退避和权限。
- 风险/不借鉴：浏览器/script 任务风险大；Release 不覆盖 Windows x86 与 OpenWrt mipsle；用户已选择暂不实现。

## 与 OneNetShare 现状对照

- 已有：WinRT 热点/legacy hosted network、指定无线网卡与有线入口拓扑、PortalGuard、IPv6Guard、HTTP UA/Client Hints/TTL/DHCP/NTP/mDNS/DNS 归一化、管理路由账本、`/status` 与 probe 日志。
- 缺口：画像一致性自检、可选出站封堵、封堵计数与证据输出、恢复耗时/在线时长、自动认证（明确暂缓）。
- 边界：HTTPS 不解密；TUN IPv4-only；Windows GUI 的 WinDivert 网络层归一化与 TUN 互斥；Linux 无法实机验证 Windows 行为。

## 第一批改造范围

1. `config.IdentityCheck`：基于默认画像检查 UA、平台、Client Hints、目标 OS、TTL、DHCP Vendor Class 是否同一画像；在 `/status` 输出 `identity=...` 和逐条 `identity_issue=...`。
2. `outbound_guard`：默认关闭；启用后由 Windows GUI 在热点接口转发层按端口/广播/组播丢弃，并统计丢弃包数；Go 侧把配置原样保留并输出状态。
3. 验证清单：LAN 面/本机面分开验证；规则存在不等于生效，必须看计数、conntrack/回显与端到端结果。

## 验证清单

### Windows 桌面热点

1. 选择画像后检查 `/status`：`identity=ok`；若切换 Android/iOS/macOS 画像，确认 `tun.ttl=64` 且 DHCP Vendor Class 不再保留 `MSFT`。
2. 开启热点后检查代理日志：UA 记录的 `original` 与 `effective` 符合画像；HTTP 204 captive 探测未外泄。
3. 若有公网 IPv6：确认 IPv6Guard 命中计数/日志；否则确认 ULA-only 或 block 策略是否生效。
4. 可选出站封堵启用后：用另一台设备访问 UDP 443（QUIC）、853（DoT）、LLMNR 5355、WS-D 3702，确认连接失败且状态中的丢弃计数增长；再确认热点本身未断网。
5. 门户排障：先抓 HAR 看 `s_is_nat`/WebRTC/ActiveX/Referer，再决定是否调整封堵；不要只看 HTTP 200 判断通网。
6. 代理/热点停止后：确认 OutboundGuard、PortalGuard、IPv6Guard、TrafficMonitor 全部停止，管理路由恢复。

### OpenWrt

1. 部署后检查 `iptables -t nat -L HOTSPOT_PROXY -n -v`、`portal_block status`、nft counter；确认 nat/mangle RETURN 在 filter DROP 之前。
2. 先 `curl` 本机与 LAN 设备两端，确认本机 OUTPUT 探活与转发面 UA 同源。
3. MTK 平台检查 `hnat hook_toggle` 与 `BIND_PPE0`，确认没有被 HNAT 卸载绕过逐包规则。
4. QUIC/组播/LLMNR/WS-D/DoT 规则先以计数模式观察，再决定是否 DROP；不要直接套用文档阈值。
5. 所有门户参数按当前网络 HAR 重抓，不继承任何仓库的固定 IP、`jsVersion`、账号前缀或错误码语义。
